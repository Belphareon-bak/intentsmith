# C.3 Channel Adapter Contract

> **Version:** 1.0
> **Status:** NORMATIVE
> **Last Updated:** 2026-02-07

This document defines the system contract for Channel Adapters in C.3. It is not API documentation—it is a binding specification that governs what adapters MUST and MUST NOT do.

---

## 1. Purpose & Role

**Channel Adapter = I/O gateway ONLY.**

A Channel Adapter is a thin bridge between an external communication channel (Slack, Discord, CLI, Web) and the internal C.3 system. It has exactly one job: translate external messages to internal events and vice versa.

The adapter:
- ✅ Receives messages from external channel
- ✅ Normalizes input to `C3InputEvent`
- ✅ Forwards events to C.3 pipeline
- ✅ Renders `C3OutputEvent` for channel capabilities
- ✅ Manages connection lifecycle
- ✅ Enforces channel-specific rate limits

The adapter does NOT:
- ❌ Make decisions
- ❌ Store conversation state
- ❌ Call tools or Executor
- ❌ Retry C.3 logic
- ❌ Route to agents
- ❌ Implement business logic
- ❌ Access memory or planner

## 2. Authority Boundaries

### Position in Architecture

```
[ External Channel ]
        ↓
  Channel Adapter        ← THIS CONTRACT
        ↓
   Input Validator
        ↓
    ChatController       ← HumanGate
        ↓
       CRE
        ↓
  Worker / TaskAgent
        ↓
     Executor
```

### Authority Matrix

| Component | Authority |
|-----------|-----------|
| Channel Adapter | I/O translation, rate limiting, connection lifecycle |
| Input Validator | Schema validation, sanitization |
| ChatController | Mode detection, safety check, handler dispatch |
| CRE | Decision making, routing |
| Executor | Tool execution |

### Adapter MUST NOT

1. **Call CRE directly** — routing is ChatController's job
2. **Call Executor** — adapter is input/output only
3. **Store conversation** — that's ConversationStore's job
4. **Implement retry logic** — C.3 handles its own retries
5. **Make routing decisions** — pass events, don't interpret them
6. **Cache responses** — caching is a separate concern
7. **Authenticate users** — that's Auth layer's job (adapter only passes identity)

## 3. C3InputEvent (Normative)

Every message entering C.3 MUST be normalized to this schema.

### Schema

```typescript
interface C3InputEvent {
  // === Identification (REQUIRED) ===
  correlationId: string;           // UUID v4, generated by adapter
  timestamp: number;               // Unix milliseconds

  // === Source (REQUIRED) ===
  source: {
    channel: 'slack' | 'discord' | 'cli' | 'web' | 'api';
    channelId?: string;            // Slack channel, Discord guild
    threadId?: string;             // Thread/conversation ID
    messageId: string;             // Original message ID for correlation
  };

  // === User (REQUIRED) ===
  user: {
    externalId: string;            // Channel-specific user ID
    displayName?: string;          // Human-readable name
    // NO email, NO tokens — auth layer handles that
  };

  // === Content (REQUIRED) ===
  content: {
    type: 'text' | 'file' | 'reaction' | 'command';
    text?: string;                 // Message text (for type: text/command)
    attachments?: Attachment[];    // For type: file
    reaction?: string;             // For type: reaction
  };

  // === Routing Hints (OPTIONAL) ===
  hints?: {
    mentionedBot: boolean;         // Was @bot mentioned?
    isDM: boolean;                 // Direct message?
    isEdit: boolean;               // Edited message?
    isReply: boolean;              // Reply to previous message?
    replyToMessageId?: string;     // Original message being replied to
  };

  // === Channel Capabilities (REQUIRED) ===
  capabilities: ChannelCapabilities;
}

interface Attachment {
  type: 'image' | 'document' | 'code' | 'audio' | 'video';
  url: string;
  mimeType: string;
  filename?: string;
  size?: number;                   // Bytes
}
```

### Validation Rules

**Validated BY adapter (before forwarding):**
- `correlationId` is valid UUID v4
- `timestamp` is positive integer
- `source.channel` is known channel type
- `source.messageId` is non-empty
- `user.externalId` is non-empty
- `content.type` is valid
- `content.text` is non-empty for type `text`/`command`
- `capabilities` is complete

If validation fails, adapter MUST NOT forward event. Log error and respond with channel-appropriate error message.

## 4. C3OutputEvent (Normative)

Every response from C.3 is delivered as this schema.

### Schema

```typescript
interface C3OutputEvent {
  // === Correlation (REQUIRED) ===
  correlationId: string;           // Echo of input correlationId
  timestamp: number;

  // === Content (REQUIRED) ===
  content: {
    type: 'text' | 'structured' | 'error';
    text?: string;                 // Plain text response
    markdown?: string;             // Markdown-formatted response
    structured?: unknown;          // Structured data (JSON)
  };

  // === Metadata (REQUIRED) ===
  metadata: {
    speaker: 'system' | 'expert' | 'agent';
    mode: 'conversation' | 'project' | 'expert' | 'agent';
    confidence: number;            // 0.0 - 1.0
    canExecute: boolean;           // Contains executable actions?
  };

  // === Delivery Hints (OPTIONAL) ===
  delivery?: {
    ephemeral: boolean;            // Only visible to sender?
    replyTo?: string;              // Thread/reply target
    priority: 'normal' | 'high';   // Affects rendering
  };
}
```

### Rendering Rules

Adapter MUST render output according to `capabilities`:

| Capability | Rendering |
|------------|-----------|
| `markdown: true` | Use `content.markdown` if available |
| `markdown: false` | Use `content.text` only |
| `threading: true` | Use `delivery.replyTo` if set |
| `maxMessageLength` | Split if exceeds, add continuation |

## 5. C3ErrorEvent (Normative)

Errors are communicated via this schema.

### Schema

```typescript
interface C3ErrorEvent {
  // === Correlation (REQUIRED) ===
  correlationId: string;
  timestamp: number;

  // === Error Info (REQUIRED) ===
  source: 'validation' | 'timeout' | 'rate_limit' | 'auth' | 'internal';
  code: string;                    // Machine-readable error code

  // === Messages (REQUIRED) ===
  userMessage: string;             // Safe to display to user
  debugInfo?: unknown;             // For logging only, NEVER display

  // === Recovery (OPTIONAL) ===
  retryable: boolean;
  retryAfterMs?: number;           // Hint for retry timing
}
```

### Error Codes

| Code | Source | Meaning |
|------|--------|---------|
| `INVALID_INPUT` | validation | Input failed schema validation |
| `EMPTY_MESSAGE` | validation | No content provided |
| `RATE_LIMITED` | rate_limit | Too many requests |
| `AUTH_FAILED` | auth | User authentication failed |
| `AUTH_FORBIDDEN` | auth | User not authorized |
| `TIMEOUT` | timeout | Processing timed out |
| `INTERNAL_ERROR` | internal | Unhandled internal error |

### Error Rendering

Adapter MUST:
- Display `userMessage` to user
- Log `debugInfo` (if present) to audit trail
- Respect `retryAfterMs` for rate limit errors
- Never expose internal error details to users

## 6. ChannelCapabilities (Normative)

Every adapter MUST declare its channel's capabilities.

### Schema

```typescript
interface ChannelCapabilities {
  // === Text Formatting ===
  markdown: boolean;               // Supports markdown?
  codeBlocks: boolean;             // Supports ```code```?
  maxMessageLength: number;        // Max chars per message

  // === Threading ===
  threading: boolean;              // Supports threaded replies?
  maxThreadDepth: number;          // 0 = flat, 1+ = nested

  // === Rich Content ===
  embeds: boolean;                 // Supports rich embeds?
  reactions: boolean;              // Supports emoji reactions?
  attachments: boolean;            // Supports file attachments?
  maxAttachmentSize: number;       // Bytes, 0 = not supported

  // === Visibility ===
  ephemeral: boolean;              // Supports ephemeral messages?
  editing: boolean;                // Can edit sent messages?
  deletion: boolean;               // Can delete sent messages?

  // === Identity ===
  userMentions: boolean;           // Can @mention users?
  channelMentions: boolean;        // Can @channel?
}
```

### Reference Capabilities

| Capability | Slack | Discord | CLI | Web |
|------------|-------|---------|-----|-----|
| markdown | ✅ | ✅ | ❌ | ✅ |
| codeBlocks | ✅ | ✅ | ❌ | ✅ |
| maxMessageLength | 40000 | 2000 | ∞ | ∞ |
| threading | ✅ | ✅ | ❌ | ✅ |
| embeds | ✅ | ✅ | ❌ | ✅ |
| reactions | ✅ | ✅ | ❌ | ✅ |
| ephemeral | ✅ | ❌ | ❌ | ✅ |
| editing | ✅ | ✅ | ❌ | ❌ |

## 7. Auth & Identity Mapping

### Separation of Concerns

```
Channel Adapter                    Auth Layer
      │                                 │
      │  user.externalId ──────────────►│
      │                                 │
      │◄────────────── C3User (or null) │
      │                                 │
      └─────► Forward event with C3User │
```

### Adapter Responsibilities

Adapter MUST:
- Extract `externalId` from channel (Slack user ID, Discord author ID)
- Pass `externalId` to Auth layer
- Receive `C3User` or `null` (unauthenticated)
- Include `C3User` in event if authenticated

Adapter MUST NOT:
- Store tokens or credentials
- Validate permissions
- Map users to roles
- Cache auth decisions

### Identity Mapping Schema

```typescript
interface IdentityMapping {
  externalId: string;              // Channel-specific ID
  channel: string;                 // Source channel
  c3UserId?: string;               // Mapped C.3 user (if authenticated)
  mappedAt?: number;               // When mapping was established
}
```

## 8. Rate Limiting & Backpressure

### Per-Channel Rate Limits

Each adapter MUST enforce channel-specific rate limits:

| Channel | Rate Limit | Burst | Cooldown |
|---------|------------|-------|----------|
| Slack | 1 msg/sec | 5 | 60s |
| Discord | 5 msg/5sec | 10 | 30s |
| CLI | No limit | - | - |
| Web | 10 msg/sec | 20 | 10s |

### Implementation Requirements

```typescript
interface RateLimiter {
  // Check if request can proceed
  canProceed(userId: string): boolean;

  // Record a request
  record(userId: string): void;

  // Get current status
  status(userId: string): {
    remaining: number;
    resetAt: number;              // Unix ms
    limited: boolean;
  };
}
```

### Backpressure Handling

When rate limited:
1. Return `C3ErrorEvent` with `source: 'rate_limit'`
2. Set `retryAfterMs` appropriately
3. Do NOT queue — reject immediately
4. Log to audit trail

When C.3 is slow:
1. Implement request timeout (default: 30s)
2. Return timeout error if exceeded
3. Do NOT retry on behalf of user

## 9. Lifecycle & Health

### Adapter Interface

```typescript
interface ChannelAdapter {
  // === Lifecycle ===
  start(): Promise<void>;
  stop(): Promise<void>;
  restart(): Promise<void>;

  // === Status ===
  status(): AdapterStatus;
  healthCheck(): Promise<HealthResult>;

  // === Event Handling ===
  onMessage(callback: (event: C3InputEvent) => Promise<void>): void;
  sendResponse(event: C3OutputEvent): Promise<void>;
  sendError(event: C3ErrorEvent): Promise<void>;

  // === Metrics ===
  getMetrics(): AdapterMetrics;
}

type AdapterStatus = 'starting' | 'connected' | 'degraded' | 'offline' | 'stopped';

interface HealthResult {
  healthy: boolean;
  latencyMs: number;
  lastError?: string;
  checkedAt: number;
}

interface AdapterMetrics {
  messagesReceived: number;
  messagesSent: number;
  errorsCount: number;
  avgLatencyMs: number;
  uptime: number;                  // Seconds
}
```

### Lifecycle State Machine

```
  ┌──────────┐
  │ stopped  │◄────────────────────────┐
  └────┬─────┘                         │
       │ start()                       │ stop()
       ▼                               │
  ┌──────────┐                         │
  │ starting │                         │
  └────┬─────┘                         │
       │ connection established        │
       ▼                               │
  ┌──────────┐     error      ┌────────┴──┐
  │connected │───────────────►│  degraded │
  └────┬─────┘                └─────┬─────┘
       │                            │
       │◄───────────────────────────┘
       │        recovered
       │
       │ stop()
       ▼
  ┌──────────┐
  │ stopped  │
  └──────────┘
```

### Reconnection Policy

On connection loss:
1. Transition to `degraded`
2. Attempt reconnect with exponential backoff
3. Max 5 attempts, then stay `degraded`
4. Manual `restart()` to retry

Backoff schedule: 1s, 2s, 4s, 8s, 16s

## 10. Non-Goals

The adapter explicitly does NOT implement:

| Feature | Reason | Where It Belongs |
|---------|--------|------------------|
| Conversation state | Adapter is stateless | ConversationStore |
| Session management | Adapter has no sessions | ChatController |
| Tool execution | Adapter is I/O only | Executor |
| Decision making | Adapter passes events | CRE |
| Retry logic | Adapter is single-shot | Runner |
| Response caching | Adapter is pass-through | Cache layer |
| User authentication | Adapter only passes identity | Auth layer |
| Permission checking | Adapter has no access control | Auth layer |
| Business logic | Adapter is infrastructure | ChatController |
| Memory access | Adapter has no knowledge | Memory layer |

If any of these features are needed, they MUST be implemented outside the adapter.

---

## 11. Invariants

These properties MUST hold at all times:

1. **Stateless**: Adapter holds no conversation state between messages
2. **Normalized**: All input is converted to `C3InputEvent`
3. **Rendered**: All output uses `ChannelCapabilities` for formatting
4. **Rate-limited**: Per-channel limits are always enforced
5. **Correlated**: Every response includes matching `correlationId`
6. **Bounded**: Request processing has timeout
7. **Observable**: Lifecycle and health are always queryable
8. **Recoverable**: Connection loss triggers automatic reconnect
9. **Isolated**: Adapter failures don't crash C.3 core
10. **Audited**: All events are logged to audit trail

## 12. Implementation Checklist

When implementing a Channel Adapter, verify:

- [ ] `C3InputEvent` schema validation
- [ ] `correlationId` generation (UUID v4)
- [ ] `ChannelCapabilities` declaration
- [ ] Output rendering respects capabilities
- [ ] Rate limiter implementation
- [ ] Lifecycle methods (start/stop/restart)
- [ ] Health check endpoint
- [ ] Reconnection with backoff
- [ ] Error event handling
- [ ] Audit trail logging
- [ ] No conversation state
- [ ] No CRE/Executor calls
- [ ] No business logic

## Appendix A: Example Implementation Skeleton

```typescript
class SlackAdapter implements ChannelAdapter {
  #status: AdapterStatus = 'stopped';
  #rateLimiter = new RateLimiter({ perSecond: 1, burst: 5 });
  #messageCallback?: (event: C3InputEvent) => Promise<void>;

  readonly capabilities: ChannelCapabilities = {
    markdown: true,
    codeBlocks: true,
    maxMessageLength: 40000,
    threading: true,
    maxThreadDepth: 1,
    embeds: true,
    reactions: true,
    attachments: true,
    maxAttachmentSize: 1_000_000_000, // 1GB
    ephemeral: true,
    editing: true,
    deletion: true,
    userMentions: true,
    channelMentions: true,
  };

  async start(): Promise<void> {
    this.#status = 'starting';
    // Connect to Slack...
    this.#status = 'connected';
  }

  async stop(): Promise<void> {
    // Disconnect...
    this.#status = 'stopped';
  }

  onMessage(callback: (event: C3InputEvent) => Promise<void>): void {
    this.#messageCallback = callback;
  }

  // Called by Slack event listener
  private async handleSlackMessage(slackEvent: SlackMessageEvent): Promise<void> {
    // Normalize to C3InputEvent
    const event: C3InputEvent = {
      correlationId: crypto.randomUUID(),
      timestamp: Date.now(),
      source: {
        channel: 'slack',
        channelId: slackEvent.channel,
        threadId: slackEvent.thread_ts,
        messageId: slackEvent.ts,
      },
      user: {
        externalId: slackEvent.user,
        displayName: await this.getUserName(slackEvent.user),
      },
      content: {
        type: 'text',
        text: slackEvent.text,
      },
      hints: {
        mentionedBot: slackEvent.text.includes(`<@${this.botId}>`),
        isDM: slackEvent.channel_type === 'im',
        isEdit: false,
        isReply: !!slackEvent.thread_ts,
      },
      capabilities: this.capabilities,
    };

    // Forward to C.3
    await this.#messageCallback?.(event);
  }
}
```

## Appendix B: Implementation Order

1. **CLI Adapter** (first)
   - No API keys
   - No network
   - Easy debugging
   - Validates contract

2. **Web Adapter** (refactor existing)
   - HTTP/WebSocket
   - Already working
   - Normalize to contract

3. **Slack Adapter** (after CLI validated)
   - Real-world testing
   - Rate limit complexity
   - Threading support

4. **Discord Adapter** (after Slack)
   - Similar to Slack
   - Different limits
   - Guild structure
