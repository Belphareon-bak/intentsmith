# Notifications System

> Core 1.0 notification contract at the WP026 C2+C4 source checkpoint. C3
> migration/apply, final behavior evidence, Review A/B, and promotion are still
> pending. External delivery remains governed by the WP027 default-off support
> policy; WP028 webhook HMAC semantics are unchanged.

## What remains supported

`in_app` delivery is always local. The retained external channel names are
`email`, `telegram`, `push`, `webhook`, and `desktop`; each is disabled unless
its exact WP027 flag is the literal string `true`:

| Channel | Opt-in | Transport |
|---|---|---|
| `email` | `C3_ENABLE_NOTIFICATION_EMAIL` | nodemailer SMTP |
| `telegram` | `C3_ENABLE_NOTIFICATION_TELEGRAM` | Telegram Bot API |
| `push` | `C3_ENABLE_NOTIFICATION_PUSH` | ntfy-compatible HTTP |
| `webhook` | `C3_ENABLE_NOTIFICATION_WEBHOOK` | WP028 HMAC-signed HTTP POST |
| `desktop` | `C3_ENABLE_NOTIFICATION_DESKTOP` | local desktop notification |

The dormant `src/notifications/channels/ntfy.js` implementation is not a
registered production channel. `push` is the supported ntfy transport and
`C3_NTFY_SERVER` is its canonical server key. Slack, Discord, SMS, and the
legacy `ntfy` channel name are not enabled by notification configuration.

Two explicit delivery paths remain:

- `POST /api/notifications/test` and `POST /api/notifications/send` may carry a
  caller-supplied recipient/destination for that request;
- an `AgentRunner` typed `notify` action may carry its own channel and
  caller-supplied recipient.

A caller-supplied destination is not written into notification configuration or
generic `user_settings`. It is not proof that the destination is absent from
delivery data: the notification log and other residual tables can retain it, as
described below.

## Hard compatibility consequence

**Automatic lifecycle/worker emails formerly generated by the
`NotificationEmitter` bridge are retired and are no longer configurable at all
in core 1.0.** The runtime notification credential setter, repository writer,
emitter injection, and lifecycle/worker emitter call graph have been removed.
There is no replacement `EMAIL_TO`, `C3_TEST_EMAIL`, or other runtime default
recipient key.

This is an intentional consequence of the accepted in-app-only automatic core
scope, not a claim that all notification delivery was removed. Manual test/send
with a caller-supplied destination and typed `AgentRunner` notification delivery
remain available, subject to the WP027 channel opt-in.

## Immutable startup credential authority

The notification authority contains exactly these 12 canonical keys:

```text
C3_SMTP_HOST
C3_SMTP_PORT
C3_SMTP_USER
C3_SMTP_PASS
C3_SMTP_FROM
C3_TELEGRAM_BOT_TOKEN
C3_TELEGRAM_CHAT_ID
C3_NTFY_SERVER
C3_NTFY_TOPIC
C3_NTFY_TOKEN
C3_WEBHOOK_URL
C3_WEBHOOK_SECRET
```

The runtime captures one frozen snapshot at startup. Precedence is exact:

1. An own property on the startup process environment wins, including the
   empty string. Its status source is `PROCESS_ENV`; an empty string has
   `configured:false` and deliberately shadows the root file.
2. Otherwise the only fallback is the exact project-root `.env`, independent of
   the launch `cwd` and `DOTENV_CONFIG_PATH`. Its status source is
   `ROOT_ENV_FILE`, including when the file or key is absent.
3. `configured` is true only when the selected value is a non-empty string.

The root file is read once through the bounded regular-file, current-owner,
single-link, exact-mode-`0600`, no-follow reader. Canonical notification values
and the eight legacy aliases below are not copied into ambient `process.env`.
The raw snapshot is private, non-enumerable, and non-serializable; channels,
server, workers, and verifier receive the same injected authority. A change to
the process environment or root `.env` therefore requires a server and worker
restart.

`configured` reports value presence only. It does not prove syntax, network
reachability, authentication, recipient validity, channel opt-in, registration,
or successful delivery. Likewise, `GET /api/notifications/channels` is only a
policy/registration view. Its historical `configured` field is not credential
readiness and is not a second secret-status API.

The `C3_WEBHOOK_SECRET` leaf is the same status snapshot used by the existing
WP028 signer. WP026 does not change the Security route, signing response, or
HMAC behavior.

## Read-only HTTP status

`GET /api/notifications/config` returns one top-level key, `sources`. `sources`
has exactly the 12 canonical keys above. Every leaf has exactly two fields:

```json
{"configured":false,"source":"ROOT_ENV_FILE"}
```

The response never contains raw values, masked fragments, derived readiness,
support flags, DB revision, or legacy aliases. In particular,
`C3_DESKTOP_NOTIFICATIONS`, `C3_TEST_EMAIL`, `C3_NTFY_URL`, `SMTP_URL`, and
`EMAIL_TO` are not status keys.

`POST /api/notifications/config` is retired before body parsing and returns the
exact response:

```http
HTTP/1.1 410 Gone
Content-Type: application/json

{"ok":false,"code":"CREDENTIAL_SOURCE_READ_ONLY"}
```

It performs no DB, revision, cache, channel, emitter, or runtime mutation.

## Legacy environment aliases

The root environment writer recognizes exactly eight delete-only aliases:

```text
TELEGRAM_BOT_TOKEN
TELEGRAM_CHAT_ID
NTFY_SERVER
NTFY_TOPIC
EMAIL_FROM
SMTP_URL
EMAIL_TO
C3_NTFY_URL
```

They can never be created or updated by the canonical writer. They may be
deleted only after a verified `TRANSFER`, mode-`0600` `EXPORT`, or explicit
`PURGE` action. `C3_NTFY_URL` is not silently renamed to `C3_NTFY_SERVER`.
`SMTP_URL`, `EMAIL_TO`, and `C3_NTFY_URL` are unmappable and therefore permit
only `EXPORT` or `PURGE`. The migration never parses `SMTP_URL`, invents a
recipient key, or writes a `C3_ENABLE_NOTIFICATION_*` flag.

An own process alias cannot be scrubbed by a file tool. After its explicit
export/purge decision, a restart must prove that the alias is absent before a
matching legacy copy can be declared scrubbed.

## Offline migration and receipt flow

The required migration is an operator-controlled offline flow, not an HTTP,
WebSocket, or loopback route:

1. A read-only census identifies each exact legacy source without printing its
   value and binds each item to a value digest.
2. The operator chooses `TRANSFER`, `EXPORT`, or `PURGE` for every item and
   confirms the complete digest-bound manifest. `PURGE` is never a default.
3. Apply requires explicit attestation that server and workers are stopped.
   Conflicts, stale values, ambiguous mappings, invalid permissions, or failed
   readback stop without partial source scrub.
4. A transfer verifies the canonical readback before removing the legacy
   source. An export creates and rechecks a new absolute, owner-owned,
   single-link, no-follow mode-`0600` file. A purge requires explicit path and
   value-digest confirmation.
5. Recovery is staged roll-forward. It never restores a secret to a legacy
   source and never claims a cross-filesystem/SQLite transaction.

At the current C2+C4 source checkpoint, the runtime cutover and offline
Architect receipt applier are present, but the C3 migration CLI/apply closeout
is not complete. Do not treat this procedure or the UI receipt support as proof
that any operator data has already been transferred, exported, purged, or
scrubbed.

Legacy `localStorage['paiass_settings']` is handled only through an explicit
absolute owner-owned mode-`0600` input file. Raw bytes never travel through
HTTP, WebSocket, a loopback connector, URL, log, clipboard automation, or an
in-app raw download. `c3-settings` is not this credential blob.

The exact sensitive paths are:

```text
notifications.emailAddresses
notifications.telegramToken
notifications.telegramChatId
notifications.slackWebhook
notifications.slackChannel
notifications.discordWebhook
notifications.webhookUrl
notifications.smsApiKey
notifications.smsSecret
notifications.smsPhone
```

The offline tool produces a non-secret
`INTENTSMITH_LEGACY_CREDENTIAL_RECEIPT/V1` receipt bound to source
`PAIASS_SETTINGS`, preimage and postimage SHA-256 digests, sorted unique path
IDs, per-path value digests, and one common `EXPORT` or `PURGE` action. A mixed
plan uses an ordered export receipt followed by a purge receipt. The Architect
applier verifies the receipt and current preimage before deleting only the
named known paths; unknown/non-secret siblings remain. Stale, malformed,
unknown-path, digest-mismatch, or storage-write failure preserves the original
blob. Reapplying the same successful receipt is accepted only for its exact
postimage digest.

## Delivery pipeline

Automatic lifecycle/worker emitter input is absent. The retained explicit
delivery paths are:

```text
POST /api/notifications/test
  -> NotificationRouter.testChannel()
  -> verify and send on the explicitly selected channel

POST /api/notifications/send
  -> NotificationRouter.send()
  -> explicitly selected channel

AgentRunner typed notify action
  -> NotificationPipeline policy (immediate / digest / drop), when injected
  -> NotificationRouter policy/registration and selected channel
  OR
  -> NotificationRouter.send() fallback when no pipeline is injected
```

Per-agent policy may still control mute, cooldown, digest, and escalation for a
typed `AgentRunner` notification routed through `NotificationPipeline`. Manual
`/test` and `/send` do not pass through that policy layer. None of these paths
restores the retired DB-configured automatic email bridge or creates a default
recipient.

## Persistent data and privacy residuals

WP026 owns notification configuration authority; it is not a global privacy
erase. These exact destinations/configuration residuals are outside its global
scrub claim:

- `notification_channels_v57.recipient` and
  `notification_channels_v57.config`;
- `notification_log_v57.recipient`;
- `notification_digest_buffer_v57.recipient`;
- persisted agent `notify` and `webhook` definitions.

SQLite freepages/WAL, historical backups, and Git history are also separate
M5-DATA/privacy work. `generic/settings/import` responses remain redacted, but
that does not prove the absence of the residual data above.

| Method | Path | Contract |
|---|---|---|
| `GET` | `/api/notifications/config` | Exact status-only 12-key `sources` map |
| `POST` | `/api/notifications/config` | Pre-parse exact `410 CREDENTIAL_SOURCE_READ_ONLY` |

| `GET` | `/api/trust/metrics/:agentId` | One agent's trust metrics |
| `POST` | `/api/trust/:agentId/unmute` | Manual unmute |

## Security invariants

- WP027 opt-in and unsupported-channel decisions remain fail-closed.
- WP028 webhook messages remain HMAC-SHA256 signed with the existing
  `X-C3-Signature` and timestamp contract.
- Credential status contains no raw or masked values.
- There is no runtime notification credential setter or emitter cache to
  invalidate.
- Caller-supplied destinations are delivery inputs, not permission to persist
  default notification configuration.
