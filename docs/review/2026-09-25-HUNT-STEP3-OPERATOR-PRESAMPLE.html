### Defect 1: Lack of Multi-Model Atomic Reservation for Cutover

**Location:** `ModelUseAuthority` class methods `acquireShared`, `acquireExclusive`, `runShared`, `runExclusive` (Lines 166–192).

**Trigger:** A binding cutover operation attempts to reserve authority over two distinct model identities simultaneously: the `previousModelName` (old artifact) and the `targetModelName` (new artifact). The caller invokes `acquireExclusive` (or `acquireShared`) for the first model, then attempts to invoke it for the second model.

**Consequence:**
1.  **Partial Acquisition:** The authority system grants a lease for the first model but holds no state regarding the second. If the second acquisition fails (e.g., due to concurrent exclusive access or validation error), the first lease remains active.
2.  **Resource Leak / Deadlock Risk:** The caller is left holding a lease for the "old" model without the "new" model. If the caller does not explicitly release the first lease before aborting, the old model remains locked (exclusive) or reserved (shared), preventing other operations (like cleanup or fallback) from proceeding.
3.  **Violation of Atomicity:** The requirement states "Both old and new artifact identities stay protected during cutover." The current implementation treats each model identity as an independent lock. There is no mechanism to reserve *both* before committing either, nor a mechanism to atomically release *both* on failure.

### Defect 2: Compensation Failure Does Not Release Leases

**Location:** `ModelUseAuthority` class, specifically the interaction between `#lease` (Line 105) and the caller's error handling in `src/upgrade/model-binding-application.js` (Lines 1740–1764).

**Trigger:** A runtime compensation event occurs after a lease has been acquired but before the operation completes. In the historical code, `this.runtime.compensate(token)` is called in a `catch` block (Line 1742).

### Defect 3: `runShared`/`runExclusive` Do Not Support Multi-Model Scopes

**Location:** `ModelUseAuthority.runShared` (Line 174) and `runExclusive` (Line 184).

**Trigger:** A cutover operation requires holding authority over *two* models (old and new) simultaneously to ensure consistency during the transition. The caller attempts to use the helper methods `runShared` or `runExclusive`.

**Consequence:**
1.  **Inability to Implement Cutover Safety:** The helper methods accept a single `inputValue` (which contains one `modelName`). They cannot be used to wrap a callback that requires locks on two different models.
2.  **Forced Manual Management:** Callers are forced to use `acquireShared`/`acquireExclusive` directly and manually manage `try/finally` blocks for multiple leases. This increases the risk of human error (forgetting to release one of the leases on an exception path), leading to the resource leaks described in Defect 1.

**Focused Reproduction:**
