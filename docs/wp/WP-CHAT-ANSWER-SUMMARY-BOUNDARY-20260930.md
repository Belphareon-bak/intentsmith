# WP — úplnost uloženého souhrnu ve finálním ANSWER promptu

**Autorita:** explicitní zadání operátora z 30. 9. 2026 dokončit funkční chat a ověřit auto-context, plus produktový závazek `PRODUCT.md` §3 zachovat historii konverzace. Tento WP je omezená oprava zjištěné regrese, nikoli nový požadavek produktu.

**Vstup:** čistý commit `09247504143ac0a37d75d7d52867768447790ad2`. V `buildAnswerContext()` je uložený souhrn při těsném 4K rozpočtu kódován stejným algoritmem jako volitelný běžný turn: zachová začátek a konec, ale tiše vynechá střed. Odpověď pak může postrádat fakt, který trvalý souhrn obsahuje.

**Vlastněné cesty:** `src/chat/handlers/decisions.js`, `tests/m1-chat-contract.test.js`, tento WP. Hunt integrační worktree mění stejnou funkci; tato změna zůstane samostatným kandidátem pro konfliktově vědomé review a integraci.

**Požadované chování:** souhrn se do finálního ANSWER provider promptu vloží beze ztráty obsahu. Běžné, volitelné turny mohou stále projít stávajícím rozpočtováním. Dlouhý `CONVERSATIONAL` turn smí přesunout právě potřebný prostor z maximálního výstupu do souhrnu, nejvýše k dolní hranici 256 tokenů. `CODE` a ostatní intenty si ponechávají dosavadní maximální výstup. Pokud se celý souhrn nevejde ani při této hranici, handler skončí před providerem typovanou chybou zpracování; nevydává odpověď ze skrytě zkráceného souhrnu ani nehlásí neexistující výpadek providera. Počet CODE retry, signál zrušení a celý aktuální user požadavek zůstávají v původní autoritě.

**Důkaz kandidáta:** pět nových/změněných M1 scénářů na vstupní revizi nejprve vykázalo `34 PASS / 4 FAIL`: prostřední fakt se ztratil v helperu i konečném provider requestu, nadlimitní souhrn tiše prošel. Navazující dlouhý konverzační případ ukázal, že prosté odmítnutí by při skutečném 4K profilu blokovalo další turny po auto-contextu. První commit `56164594` prošel 41 M1 testy, ale nezávislá revize jej označila `CHANGES_REQUIRED`: konverzační instrukce žádala přibližně 349 slov, zatímco finální provider `num_predict` po započtení souhrnu činil jen 280. Aktuální oprava iteruje výstupní strop a instrukci do shody; každá iterace smí strop pouze snížit. Deterministický M1 test nyní porovnává počet slov v reálném provider body přímo s `num_predict` za přítomnosti celého souhrnu a hlídá, že CODE obě volání zachovají `num_predict=1200` bez konverzační instrukce. Na Node 24.21.0 běží `41 PASS / 0 FAIL`. Testy dále kontrolují celý serializovaný souhrn v konečném provider promptu a typovanou lokální chybu s nulovým provider voláním pro nadlimitní souhrn. `maxTokens` zůstává horní autoritou; změna jej pro konkrétní `CONVERSATIONAL` turn smí snížit právě kvůli úplnému souhrnu. CODE výstup a retry kód se nemění. Celý souhrn dostává přednost před volitelnými výňatky nových turnů.

**Přesný vývojový limit:** read-only rekonstrukce prvního kandidáta ze soukromého předchozího živého běhu sady 85 na `09247504` ukazuje v turnu 7 souhrnný JSON řádek 1 034 B, původní rozpočet historie 282 B a konverzační strop 288 výstupních tokenů. Rekonstruovaný prompt obsahoval celý souhrn a splnil konzervativní 4K nerovnost; finální krátký recall dostal 1 200 tokenů. Opravený strop po ustálení se nad stejným živým vstupem znovu neměřil. Jde o odhad z minulých vstupních bajtů, nikoli nový modelový běh. Při větším souhrnu nebo požadavku může dolní hranice 256 tokenů vynutit terminální odmítnutí. Nezávislá revize, integrace a nový živý běh jsou následné brány, nikoli výsledek tohoto WP.

**Hranice výstupu:** instrukce o přibližném počtu slov je plánovací vodítko pro model, nikoli záruka, že model dodrží délku nebo formát. Živý test nad přesným 4K artefaktem je stále potřeba. `sourceErrorType=ANSWER_CONTEXT_SUMMARY_TOO_LARGE` a případná chyba ustálení rozpočtu jsou interní diagnózy `ChatProcessingError`; M1 HTTP v `src/routes/chat.js` a M1 WS v `src/ws-bridge/session-adapter.js` záměrně serializují jen veřejné `error.code` a `error.message`, tedy obecné `CHAT_PROCESSING_FAILED`. Tento WP nemění protokol; bez nového smluvně schváleného pole klient interní důvod nerozliší.
